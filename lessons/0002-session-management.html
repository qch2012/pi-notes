Lesson 0002 · Core workflow

Session management: branching, forking, cloning, compaction

This is the biggest structural delta from a linear-history agent. Pi sessions are trees, not a single scrollback — and three different commands let you branch off in three different ways, for three different reasons.

Why this lesson Your mission calls out "session management (branching, /tree, /fork, /clone, compaction)" by name as a fluency target. It's also the thing most likely to feel unfamiliar day one, since most terminal agents you've used treat a session as one linear thread.

1. The core idea: sessions are trees

Every message in a session has an id and a parentId. Your current position is the "active leaf." Nothing is ever overwritten — going back to an earlier point and trying something different just grows a new branch off that point, alongside the one you left.

├─ user: "Hello, can you help..."
│  └─ assistant: "Of course! I can..."
│     ├─ user: "Let's try approach A..."
│     │  └─ assistant: "For approach A..."
│     │     └─ user: "That worked..."  ← active
│     └─ user: "Actually, approach B..."
│        └─ assistant: "For approach B..."

Both "approach A" and "approach B" still exist in the same file. That persistence is what the next three commands each give you a different way to use.

2. /tree, /fork, /clone — same tree, three different moves

All three let you jump to an earlier point in a conversation. The difference is what happens to the file:

Feature/tree/fork/clone
OutputSame session fileNew session fileNew session file
What you pick fromFull treeA previous user messageCurrent active branch (whole)
Typical useExplore alternatives in placeStart a fresh session from an earlier promptDuplicate current work before continuing
Branch summary offered?Yes, optionalNoNo

Rule of thumb: staying in one file and keeping alternatives visible side by side → /tree. Wanting a clean, separate session file → /fork or /clone.

/tree in practice

Opens an interactive tree view. Selecting a user message moves the leaf to that message's parent, drops the message text into your editor so you can edit and resubmit — that's how a new branch gets created. Selecting an assistant/tool/other entry just moves the leaf there with an empty editor, so you continue from that point unchanged.

KeyAction
↑/↓Navigate visible entries
←/→Page up/down
Ctrl+←/→ or Alt+←/→Fold/unfold, jump between branch segments
Shift+LSet or clear a label on the selected entry

Branch summaries

When /tree moves you away from a branch, Pi offers to summarize the branch you're abandoning and attach that summary at your new position — so context from the path you left isn't just silently lost. You choose: no summary, default-prompt summary, or a custom-focus summary.

3. Naming, finding, and inspecting sessions

CommandFunction
/name <name>Set a human-readable name for the current session
/sessionShow session file path, session ID, message count, tokens, cost
/resumeInteractive picker for past sessions in this project
/newStart a fresh session

Startup flags do the same jobs without entering the UI first:

pi -c                    # continue most recent session
pi -r                    # browse and select from past sessions
pi --no-session          # ephemeral, nothing saved
pi --name "my task"      # set display name at startup
pi --session <path|id>   # resume a specific session
pi --fork <path|id>      # fork a specific session into a new one

In the /resume picker: type to search, Ctrl+P toggles path display, Ctrl+S toggles sort mode, Ctrl+N filters to named sessions, Ctrl+R renames, Ctrl+D deletes (with confirmation — uses the trash CLI when available, so it's usually recoverable).

Named sessions are dramatically easier to pick out of that list later — get in the habit of /name or --name on anything you'll want to find again.

4. Compaction — keeping long sessions usable

Context windows are finite. Pi handles that two ways:

  • Auto-compaction — fires automatically once context exceeds contextWindow − reserveTokens (reserve defaults to 16,384 tokens). Pi walks backwards from the newest message, keeps the most recent ~20,000 tokens (keepRecentTokens, configurable) verbatim, and summarizes everything older into a structured summary block appended to the session.
  • Manual compaction — /compact [instructions]. Same mechanism, triggered on demand. The optional instructions steer what the summary focuses on, e.g. /compact focus on the API contract decisions, drop exploratory dead ends.

Nothing is deleted — the raw messages stay in the session file, they're just excluded from what gets sent to the model going forward. The summary follows a fixed structure (Goal / Constraints / Progress / Key Decisions / Next Steps / Critical Context, plus lists of read and modified files), which is why compacted context tends to stay usably specific rather than degrading into vague recap.

Configure it in ~/.pi/agent/settings.json or <project>/.pi/settings.json:

{
  "compaction": {
    "enabled": true,
    "reserveTokens": 16384,
    "keepRecentTokens": 20000
  }
}

Set enabled: false to turn off auto-compaction entirely — you can still run /compact by hand.

5. Moving sessions around

CommandFunction
/export [file]Export session to HTML (readable transcript) or JSONL (raw, re-importable)
/import <file>Import and resume a session from a JSONL export
/shareUpload as a private GitHub gist, gives you a shareable HTML link

Note the asymmetry: /export to JSONL round-trips (you can /import it back and keep working), but the HTML export and /share link are read-only transcripts for showing someone else what happened — not something you resume from.

Retrieval check — no peeking until you've tried

Without scrolling up: which of /tree, /fork, /clone creates a new session file, and which one offers to summarize the branch you're leaving?

New session file: /fork and /clone (not /tree — it stays in the same file).
Offers a branch summary: only /tree, when it moves you off a branch.
