Lesson 0004 · Safety model

Trust and sandboxing: what Pi actually protects you from

This is the lesson most worth reading carefully before pointing Pi at a repo you don't fully control. The short version: project trust is a config-loading gate, not a sandbox — and Pi ships with no sandbox at all by default.

Why this lesson Your mission names this directly: "Understands the trust/sandboxing model well enough to use it safely on real repos." Getting this wrong is the mid-task surprise most likely to actually cost you something, unlike the other deltas which are just workflow friction.

1. Project trust: what it is

Project trust controls one thing only: whether Pi loads project-local configuration before you've had a chance to look at it. Specifically, a project is considered to have resources requiring trust if it has any of:

  • .pi/settings.json
  • .pi/extensions, .pi/skills, .pi/prompts, or .pi/themes
  • .pi/SYSTEM.md or .pi/APPEND_SYSTEM.md
  • project .agents/skills in the cwd or an ancestor directory

A bare .pi directory with none of the above doesn't trigger a trust prompt. And critically: context files load regardless of trust — AGENTS.md, CLAUDE.md, AGENTS.override.md are read whether or not you've trusted the project (unless you've disabled context loading entirely).

2. How the prompt resolves

On interactive startup, if a project has trust-requiring resources and there's no saved decision for that directory or a parent, Pi asks. Your answer can be remembered:

  • /trust in-app saves a decision to ~/.pi/agent/trust.json, keyed by canonical directory — including an option to trust the immediate parent folder too. It doesn't reload the current session; restart to take effect.
  • The closest saved decision on the current or parent path wins over the global default.
  • If nothing applies, defaultProjectTrust (global-only setting) decides: "ask" (default), "always", or "never".

Non-interactive modes (-p, --mode json, --mode rpc) never show a prompt — they fall straight to defaultProjectTrust, or you override per-run with --approve/-a or --no-approve/-na.

Trusting unlocks: loading .pi/settings.json, loading .pi resources (extensions, skills, prompts, themes, system prompt files), auto-installing missing project-configured packages, and running project-local extensions.

3. What trust does not do

This is the part to actually internalize:

Project trust is only an input-loading guard. It prevents a repository from silently changing pi's settings or extensions before you approve it. It does not make untrusted code, untrusted prompts, or untrusted model output safe.

Concretely:

  • No built-in sandbox, ever — trusted or not. Built-in tools read/write/edit files and run shell commands with your full user permissions, same as if you typed the commands yourself.
  • Declining trust doesn't stop you from working — it just skips loading that repo's own extensions/skills/settings. The model can still read, write, edit, and run bash in that directory once you're chatting with it, using your global toolset.
  • Prompt injection is an accepted, unsolved risk. Malicious instructions hidden in repo files, comments, docs, or build output are "expected local-agent risk" per the docs — trust doesn't filter this.

So trust answers "should this repo be allowed to silently reconfigure my agent," not "is it safe to let the agent operate here."

4. When you actually need isolation

For repos you don't trust, generated/untrusted code you're not watching closely, or unattended automation, the answer is OS-level isolation — a container, VM, micro-VM, or policy-controlled sandbox — not a Pi setting. Patterns documented for this:

  • Run the whole pi process inside a container/sandbox
  • Run host Pi but route built-in tool execution into a Gondolin micro-VM
  • Mount only the workspace paths the agent needs — read-only where you want a hard guarantee against unintended writes
  • Avoid mounting host ~/.pi/agent unless the container should see host sessions/settings/credentials
  • Pass minimum-scope or short-lived API keys; restrict network access when the task doesn't need it
  • Review diffs/outputs before copying results back to trusted systems

Full patterns are in Containerization — worth a read before you first point Pi at, say, a cloned PR you haven't reviewed.

5. Practical rule of thumb

For your own repos, on your own machine, that you're actively watching — the default "ask" trust flow plus normal git hygiene (review diffs before committing/pushing) is the realistic bar, same as any other terminal agent with full tool access. Reach for containerization specifically when the work is unattended, the source is untrusted, or the credentials in scope are more sensitive than the task needs.

Retrieval check — no peeking until you've tried

Without scrolling up: if you decline project trust, does that stop Pi's bash tool from running shell commands in that directory?

No. Declining trust only skips loading that project's own .pi settings/extensions/skills. The built-in tools (bash included) still run with your full user permissions regardless of the trust decision — there is no sandbox, trusted or not.
