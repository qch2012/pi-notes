Lesson 0007 · Customization

Extensions: TypeScript modules that reshape Pi's behavior

Extensions are the deep-customization layer — plain TypeScript, no build step, hot-reloadable. This is also where the six things Pi omits by default (Lesson 0001) come back, if you want them: permission gates, custom tools, MCP bridges, whatever else a full event-driven hook system can build.

Why this lesson Third of four customization lessons, and the one that closes the loop on "no permission popups by default" from Lesson 0001 — a confirm-before-rm -rf extension is the canonical first thing people write.

1. Minimal extension, end to end

~/.pi/agent/extensions/my-extension.ts:

import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";
import { Type } from "typebox";

export default function (pi: ExtensionAPI) {
  pi.on("session_start", async (_event, ctx) => {
    ctx.ui.notify("Extension loaded!", "info");
  });

  pi.on("tool_call", async (event, ctx) => {
    if (event.toolName === "bash" && event.input.command?.includes("rm -rf")) {
      const ok = await ctx.ui.confirm("Dangerous!", "Allow rm -rf?");
      if (!ok) return { block: true, reason: "Blocked by user" };
    }
  });

  pi.registerTool({
    name: "greet",
    label: "Greet",
    description: "Greet someone by name",
    parameters: Type.Object({ name: Type.String({ description: "Name to greet" }) }),
    async execute(toolCallId, params, signal, onUpdate, ctx) {
      return { content: [{ type: "text", text: `Hello, ${params.name}!` }], details: {} };
    },
  });

  pi.registerCommand("hello", {
    description: "Say hello",
    handler: async (args, ctx) => {
      ctx.ui.notify(`Hello ${args || "world"}!`, "info");
    },
  });
}

No compile step — extensions load via jiti, so TypeScript runs directly. Test a work-in-progress file without installing it anywhere permanent:

pi -e ./my-extension.ts

That single file already demonstrates the four building blocks: events (pi.on), custom tools (pi.registerTool), custom commands (pi.registerCommand), and user interaction (ctx.ui).

Files/directories placed in the auto-discovered locations support /reload hot-reloading. pi -e ./path.ts is for quick one-off testing, not permanent placement.

Three growth stages, same as any small tool: single file → directory with index.ts and helper modules → full package with its own package.json and npm dependencies (run npm install in the extension directory, then node_modules/ imports resolve automatically).

3. The event model, at a glance

Pi's lifecycle fires a long, well-defined sequence of events — session start, per-turn agent events, per-tool-call events, compaction, tree navigation, model switches. The two you'll reach for most:

  • tool_call — fires before a tool executes. event.input is mutable (patch arguments in place), and returning { block: true, reason } stops the call. This is exactly how you'd rebuild a permission-popup layer.
  • tool_result — fires after execution, before the result is finalized. Handlers chain like middleware and can modify content/details/isError.

Full event catalogue — project_trust, resources_discover, session_before_compact/session_before_tree (which is how you'd customize compaction or branch summaries from Lesson 0002), before_agent_start (inject messages or rewrite the system prompt), context (mutate outgoing messages), input (intercept raw user input before skill/template expansion) — is in the primary source. Read the lifecycle diagram there once; it clarifies ordering questions no amount of prose will.

4. ctx.ui — the interaction surface

await ctx.ui.confirm("Title", "Are you sure?");   // yes/no dialog
await ctx.ui.select("Pick one:", [...]);           // list picker
await ctx.ui.input("Prompt:");                     // free text
ctx.ui.notify("Done!", "info");                    // toast
ctx.ui.setStatus("my-ext", "Processing...");        // footer status
ctx.ui.setWidget("my-ext", ["Line 1", "Line 2"]);   // persistent widget above editor

Guard dialog methods with ctx.hasUI (false in print mode -p and JSON mode) — fire-and-forget methods like notify work in TUI and RPC but are no-ops where there's no UI to show them in.

5. Restoring what Lesson 0001 said Pi omits

All six defaults-you-don't-get are extension territory:

Omitted defaultExtension mechanism
Permission popupstool_call + ctx.ui.confirm(), exactly like the rm -rf example above
To-do / task trackingStateful custom tool via pi.registerTool() plus pi.appendEntry() for persistence across restarts
Background bashCustom tool that manages a long-lived child process, surfaced via ctx.ui.setStatus()/setWidget()
MCPAn extension that bridges MCP server tools into pi.registerTool() calls at startup
Sub-agentsctx.newSession()/ctx.fork() plus a custom tool that drives a nested agent run and returns its result
Plan modebefore_agent_start to inject planning instructions, or a custom tool that gates execution behind an approved plan

Don't build these from scratch on day one — check the package gallery (next lesson) first, since some of these are common enough to already exist as installable packages.

6. Security note

Extensions run with your full system permissions and can execute arbitrary code — same trust bar as running an unfamiliar shell script. Only install from sources you trust, and read third-party extension source before enabling it, especially anything from outside the auto-discovered project-local paths (which at least gate behind project trust, Lesson 0004).
